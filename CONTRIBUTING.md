# Development and contributing

## Environment and source installation

Use Node.js 22 or newer and DSH `0.2.2-rc.1` as the tested development baseline. Nearby DSH versions may be compatible but are not guaranteed; the [package manifest](package.json) declares install-time engine constraints. The plugin uses Node built-ins and the DSH Host/Client runtime: there are no third-party dependencies to install and no build step. Work from this repository's root; no parent workspace or sibling checkout is required.

To try a source change, install this package directory through DSH's plugin manager into a test profile. Restart DSH after Host or Client changes, then open **Settings → DSH Sync**. Use generated fixture files and a dedicated test account rather than private instructions or an everyday profile. Automated tests do not require a Microsoft account; live synchronization needs a Microsoft account, network access, and a browser on the Host machine.

Preserve `MICROSOFT_CLIENT_ID` in [the configuration module](src/config.js); changing it requires maintainer approval because it affects existing authorization. Do not change the package version after edits, tests, builds, or packaging unless the user explicitly requests it.

## Working on changes

Follow the [project instructions](AGENTS.md). Keep code, comments, documentation, and commit messages English; translated READMEs and localization values use their target languages. Keep the [Chinese](README.zh-CN.md) and [Japanese](README.ja.md) READMEs aligned with the [English version](README.md) when user-facing behavior changes. Use English Conventional Commits and keep changes focused. Do not include credentials, user assets, runtime state, local investigation notes, caches, or generated distribution archives.

The main areas are:

- `index.js` and `client.js`: Host integration and the settings page
- `src/`: synchronization, native files/tracking, crypto/device trust, authentication, and OneDrive transport
- `test/`: offline unit, filesystem, and runtime-contract tests
- `locale/` and `scripts/`: translations and contributor checks
- `docs/`: security, native-file behavior, device trust, and the storage protocol

Read the relevant [protocol](docs/protocol.md), [native-file](docs/native-assets.md), or [security](docs/security.md) contract when changing persistent data or safety-sensitive behavior. Add regression tests for changed behavior rather than recording a debugging narrative in project documentation.

## Checks

Run from the repository root:

```sh
node --test
node scripts/check.mjs
```

Tests use temporary native roots and mocked transport; Windows also tests DPAPI with generated bytes. The check validates syntax, documentation links, distribution resources, and generated translations. Offline tests do not prove live Microsoft compatibility, browser rendering, or actual registered-application launching.

For translations, edit `locale/en.json`, `locale/zh-CN.json`, and `locale/ja.json`, then regenerate embedded messages and the `zh.json` metadata alias:

```sh
node scripts/locales.mjs
```

For ordinary changes, run the automated checks and manually exercise only the affected live behavior. Documentation-only changes need the contributor check; repeat live integration tests when the integration changes. Report actual checks and remaining gaps in the change description, not in a growing repository acceptance log.

## Before a release

Use harmless fixtures and test profiles. These are release-level checks, not a form to fill out for every commit:

- Verify installation/upgrade, settings rendering and native opening, and that user-only controls remain unavailable to agent tools
- Verify two-device sign-in, automatic synchronization, conflict/backup recovery, exclusions, and optional `.agents` participation without losing unrelated files
- Verify encrypted initialization, recovery, later encryption and passphrase changes, plus Windows restart/manual-lock behavior and manual-unlock fallback
- Review package contents and known limits, include the [GPL-3.0 license](LICENSE), confirm package ownership and repository/security-contact metadata, and state only the DSH/platform/account combinations actually tested

Inspect distribution contents before publishing:

```sh
npm pack --dry-run --ignore-scripts
```

The package must not contain local data or credentials. Personal and organizational OneDrive compatibility require separate live evidence before claiming both; mocked Graph tests are not that evidence. Installation into a real profile remains a separate maintainer action.

## Automated releases

The [CI and release workflow](https://github.com/anime-fan-5903/dsh-sync/blob/main/.github/workflows/ci.yml) runs `node --test` and `node scripts/check.mjs` on Ubuntu and Windows with Node.js 22 for pull requests targeting `main` and every push to `main`. It does not install npm dependencies. GitHub's MIT-licensed `actions/checkout` v7.0.1 and `actions/setup-node` v7.1.0 are pinned to full commit SHAs and run only on hosted runners; checkout credentials are not persisted and package-manager caching is disabled. The application remains dependency-free.

A maintainer explicitly selects each release version in [the package manifest](package.json):

1. Prepare and review the changes in a pull request.
2. When the changes should ship, add a strictly higher stable `MAJOR.MINOR.PATCH` version to the PR branch, optionally as a separate `chore(release): prepare vX.Y.Z` commit. Prerelease identifiers and build metadata are not accepted by this stable-release workflow.
3. Wait for both platform checks to pass, then merge. Adding a version commit to a contributor's fork requires permission to edit that branch; otherwise ask the contributor or prepare a separate version PR.
4. The main-branch workflow compares the package versions at the push event's exact `before` and `after` commits, including pushes containing multiple commits. An unchanged version only runs checks: it does not pack, create a tag, publish a Release, or replace existing attachments. Several unversioned PRs can therefore be merged before a single version PR releases their combined changes.
5. A changed version must increase. After both platform checks pass, the [release script](scripts/release.mjs) inspects the package contents, runs `npm pack --ignore-scripts`, creates `vX.Y.Z` at the exact triggering commit, and prepares a draft GitHub Release. It uploads `dsh-sync-X.Y.Z.tgz` and `SHA256SUMS`, verifies the server-side asset sizes and SHA-256 digests, then publishes a non-prerelease Release. GitHub's legacy latest-selection policy is used rather than blindly marking whichever parallel run finishes last as latest.

Documentation, tests and CI maintenance normally do not need a version bump. Changes intended for users do. Do not infer release eligibility from changed paths: the version is the explicit release decision. Do not merge two release PRs with the same proposed version. Configure branch protection to require both platform checks and an up-to-date branch before merging; the workflow itself does not change repository settings.

Only the main push release job receives `contents: write`; PR checks receive `contents: read`. The workflow uses the automatically provided `GITHUB_TOKEN`, not a personal access token or Microsoft credentials. Repository or organization policy must allow Actions and the two pinned official actions, and must permit the release job to create tags, Releases and attachments. Tag rulesets can block publication and may need maintainer configuration. No npm registry publication or automatic plugin installation occurs. Source archives generated by GitHub are not substitutes for the attached npm distribution package.

### Retries and immutable versions

Never move a published version tag or replace its assets with another build. If publication fails, use GitHub Actions **Re-run all jobs** on that original push run so the platform checks and exact source commit are used again. The script can resume a matching tag or partial draft without overwriting verified assets. A complete matching release is a no-op. A conflicting tag, unexpected attachment, missing or different asset digest, prerelease, or incomplete already-published Release fails closed; inspect the failure rather than deleting or overwriting the old version. A newer npm/runtime producing different archive bytes on a rerun will also be rejected; use a new version if a different build must be distributed. There are no automatic retries of mutating API calls: after a timeout or conflict, rerunning first reads and validates the server state.

Initial branch creation (an all-zero `before` SHA), missing source history and force pushes are not release triggers and fail closed. The first push adding this workflow with an unchanged package version will only validate; it does not retroactively publish an existing version. Prepare a later version bump when the next release is ready. Do not introduce a new version and then remove it again within the same push: only the push's final version is considered.

The workflow's tests are offline checks, not live Microsoft-account, two-device, UI or permissions acceptance. Complete the release-level checks above as appropriate before merging a release PR; automated release notes state the CI coverage and its live-test limits.
