# Development and contributing

## Environment and source installation

Use Node.js 22 or newer and DSH `0.2.2-rc.1` as the tested development baseline. Nearby DSH versions may be compatible but are not guaranteed; the [package manifest](package.json) declares install-time engine constraints. The plugin uses Node built-ins and the DSH Host/Client runtime: there are no third-party dependencies to install and no build step. Work from this repository's root; no parent workspace or sibling checkout is required.

To try a source change, install this package directory through DSH's plugin manager into a test profile. Restart DSH after Host or Client changes, then open **Settings → DSH Sync**. Use generated fixture files and a dedicated test account rather than private instructions or an everyday profile. Automated tests do not require a Microsoft account; live synchronization needs a Microsoft account, network access, and a browser on the Host machine.

Preserve `MICROSOFT_CLIENT_ID` in [the configuration module](src/config.js); changing it requires maintainer approval because it affects existing authorization. Do not change the package version after edits, tests, builds, or packaging unless the user explicitly requests it.

## Working on changes

Follow the [project instructions](AGENTS.md). Keep code, comments, documentation, and commit messages English; translated READMEs and localization values use their target languages. Keep the [Chinese](README.zh-CN.md) and [Japanese](README.ja.md) READMEs aligned with the [English version](README.md) when user-facing behavior changes. Use English Conventional Commits and keep changes focused. Do not include credentials, user assets, runtime state, local investigation notes, caches, or generated distribution archives.

The main areas are:

- `index.js` and `client.js`: Host integration and the settings page
- `src/`: synchronization, native files/tracking, crypto/device trust, authentication, and OneDrive transport
- `test/`: offline unit, filesystem, and runtime-contract tests
- `locale/` and `scripts/`: translations and contributor checks
- `docs/`: security, native-file behavior, device trust, and the storage protocol

Read the relevant [protocol](docs/protocol.md), [native-file](docs/native-assets.md), or [security](docs/security.md) contract when changing persistent data or safety-sensitive behavior. Add regression tests for changed behavior rather than recording a debugging narrative in project documentation.

## Checks

Run from the repository root:

```sh
node --test
node scripts/check.mjs
```

Tests use temporary native roots and mocked transport; Windows also tests DPAPI with generated bytes. The check validates syntax, documentation links, distribution resources, and generated translations. Offline tests do not prove live Microsoft compatibility, browser rendering, or actual registered-application launching.

For translations, edit `locale/en.json`, `locale/zh-CN.json`, and `locale/ja.json`, then regenerate embedded messages and the `zh.json` metadata alias:

```sh
node scripts/locales.mjs
```

For ordinary changes, run the automated checks and manually exercise only the affected live behavior. Documentation-only changes need the contributor check; repeat live integration tests when the integration changes. Report actual checks and remaining gaps in the change description, not in a growing repository acceptance log.

## Before a release

Use harmless fixtures and test profiles. These are release-level checks, not a form to fill out for every commit:

- Verify installation/upgrade, settings rendering and native opening, and that user-only controls remain unavailable to agent tools
- Verify two-device sign-in, automatic synchronization, conflict/backup recovery, exclusions, and optional `.agents` participation without losing unrelated files
- Verify encrypted initialization, recovery, later encryption and passphrase changes, plus Windows restart/manual-lock behavior and manual-unlock fallback
- Review package contents and known limits, include the [GPL-3.0 license](LICENSE), confirm package ownership and repository/security-contact metadata, and state only the DSH/platform/account combinations actually tested

Inspect distribution contents before publishing:

```sh
npm pack --dry-run --ignore-scripts
```

The package must not contain local data or credentials. Personal and organizational OneDrive compatibility require separate live evidence before claiming both; mocked Graph tests are not that evidence. Publishing or installing into a real profile is a separate maintainer action, not a consequence of passing these checks.
